**Baseline:** R10 (tag `v5.3.0-private-r10`). R5, R7, R8, R9 and R10 stay as tags.

**Evidence labels:**

## 3. Module 1: PT: Second Bounce Coverage (EXPERIMENTAL; Native / Auto = 100 %, 50 %, 25 %; next start; no Quick Preset)
**Where the work is (STATIC, `PTRGSFinal` / `PTRGSWithSERFinal`):**
* The PT ray generation runs one loop iteration per bounce: header `%908`, counter `%963` from 0, exit test `counter + 1 < bounces`.
* `bounces` is the `select(hair, 4, 2)` that URT's PT library already turns into `select(hair, %rpt_nh, %rpt_nb)` (CameraCB rows 33 and 56).
* Each extra iteration traces one bounce ray, shades its hit and traces its light (shadow) rays. That is the work behind the measured 47 → 57 FPS.

**What changes:** for non-hair pixels the bounce limit becomes `selected ? %rpt_nb : min(%rpt_nb, 1)`.
* "Selected" = `((x + y + y/2 + frame) & (2^level − 1)) == 0`, with `frame` = CameraCB row 13 .w (the counter the game's own PT checkerboard uses).
* **50 %:** every second pixel per frame. **25 %:** every fourth.
* The pattern moves every frame, so each pixel gets its full bounces once every 2 or 4 frames, and DLSS Ray Reconstruction accumulates them temporally.
* Unselected pixels render exactly what Geometry Bounces 1 renders for them: a shader state the game already supports.
* Hair keeps its own count.
* No TraceRay, loop, resource or binding is added; only how many loop iterations run per pixel changes.

**Expected cost (not measured):** roughly 50 % or 25 % of the second bounce's cost, i.e. between the 2-bounce and 1-bounce results.

**Expected look:**
* Indirect light keeps much of the 2-bounce brightness and colour, because the 2-bounce samples are still there, rotating, and accumulated by RR.
* It may be noisier, or show a faint rotating pattern in dark bounce-lit areas.
* It is not an unbiased estimator: the average lies between the 1-bounce and 2-bounce images.

**Mechanism:**
1. **At ASI load (PT shader preparation), option not Native:**
   * URT builds its normal PT library exactly as before (validated SHA-256 `f1ad5c37…`);
   * then a variant with the game's DXC: disassemble → coverage edit → Orange Hair Fix's hair patch (§4) → assemble → URT library's other container parts → validate and sign → disassemble again and check both edits in both exports;
   * the variant is installed in the same two PT shader slots (it must fit the slot: native 231144 bytes + 22144 zero bytes).
2. **Level transport:** the level travels in bits 16–17 of URT's existing CameraCB bounce word (gate: in-function bridge and post-serialize). URT's normal library reads bits 0–15 only.
3. **Native / Auto:** the unchanged URT library, bit-identical to R10 (Orange Hair Fix keeps recognising it by hash, its "Path B").
4. **Master Off, leaving PT, or the game's SHaRC on:** the gate writes nothing, so the level is 0 and every pixel gets every bounce.
5. **Startup guard:** the same file and rules. It is decided at ASI load, and the runtime boot step keeps that record and proves it after 10 minutes of RT/PT.
   * A start that cannot prepare the PT shader (late attach) turns a PENDING record into FAILED.
   * A failed variant build drops the record and logs it; URT's normal library is used.

**Log proof** (`bin\x64_dx12\UltimateRefinedTracing.log`):
1. `PT: Second Bounce Coverage requested (level 1)` (level 2 = 25 %)
2. `PT: Second Bounce Coverage 50% active: variant PT library validated (N bytes) and installed; Orange Hair Fix's PT hair patch is built in`
3. `PT shader slots installed; URT's PT library variant for PT: Second Bounce Coverage …`

**Failure lines:**
* `could not be prepared …`: the normal library is used.
* `startup guard: … URTX_ExpPTSecondBounce=… not applied`: set Native / Auto for one start.

## 4. Orange Hair Fix compatibility (its documented Path A)
* Orange Hair Fix replaces URT's PT library only when it matches by hash (502a7218…, its "Path B"). Any changed URT library would leave hair orange in PT.
* Orange Hair Fix's own handoff (§5, "Path A: Refined Tracing bakes the hair patch into its own PT shaders (recommended)") specifies exactly this. R11 does it for the variant only.
* `urt_ohf_bake` is a line-for-line C port of its `patch_pt.py`, RELEASE build:
  * cb12[338].y: 0 / 77 off, 25 / 50 / 75 %, 90 = 100 %;
  * class 3;
  * the skin-desaturation flag and its 4 strength sites per export;
  * it refuses a second application (its rule).
* **OFFLINE:** on the real library text the port's output is **identical** to `patch_pt.py`'s (`v5311_ohf_equivalence`).
* Without the hair mod its menu value stays 0, so there is no change.
* Orange Hair Fix's plugin then passes the variant through unchanged (unknown hash), so the patch is never applied twice.

**Immersive World** ships no DXR library and touches neither the PT ray generation nor the gate (compat evidence test passes).

## 5. Objective B: below one-bounce cost (investigated; not implemented in R11)
* **The loop always runs at least once** (bottom-tested), and values from iteration 0 feed the post-loop outputs that Ray Reconstruction reads (STATIC: loop-carried values `%910`–`%917`). A "first-bounce coverage" therefore needs the loop restructured and RR guides synthesised for skipped pixels, which is a high risk of RR artefacts. Not built without evidence.
* **Next candidates with the same mechanism** (no new rays, per-pixel limits only):
  * shadow-ray (light-sample) coverage at the bounce vertex (flags 12 / 28 sites inside the loop);
  * the measured PT Shadows Off delta (about +4 FPS) bounds what shadow-ray savings can give.
* **Not feasible:**
  * lower-resolution PT dispatch (RR guide sizes);
  * opacity micromaps (R8).
* Foliage any-hit work was shown not to matter (R8).
