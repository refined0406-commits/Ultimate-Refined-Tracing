# V5.3.0 PRIVATE R4: RT Animated Geometry Trace Mode crash: findings, recovery, repair

## 1. Recover the game now
URT has no copy of this choice in its own file. The menu stores it in the game's `dx12user.settings`, section `[URTExtended]`, as `URTX_RTASFastTrace=1`. Every launch, URT reads it from there. You asked not to touch that file, so the recovery goes through the game's own menu.
1. *(Optional, helps the diagnosis)* Launch once more. After the crash, copy two things:
   * `bin\x64_dx12\UltimateRefinedTracing.log`. URT rewrites it at every start, so a new "session started" time shows URT got that far.
   * Windows Event Viewer → Windows Logs → Application → the "Application Error" for `witcher3.exe`: faulting module and exception code.
2. In `bin\x64_dx12`, rename `UltimateRefinedTracing.asi` to `UltimateRefinedTracing.asi.off`. URT is now not loaded, and nothing writes the engine flag.
3. Start the game.
   * **If it still crashes:** URT's setting is not the cause, because with URT disabled the flag stays at the game's value. Send the Event Viewer entry.
   * **If it starts:** Options → mod menu → RT Animated Geometry Trace Mode → **Native / Auto**. Leave through the menu so the game saves, then quit.
4. Install R4 (MAIN or ASI-ONLY, as before). It replaces the `.asi`; delete the `.asi.off` copy.

Nothing else changes:
* All other URT choices stay as they are; they live in the same section and in `UltimateRefinedTracing.settings`, and neither is touched.
* No native graphics setting is touched.
* No reinstall is needed and no other mod is removed.

## 2. Investigation
**Confirmed** (static analysis of Patch 5.01 + your log)
* **The setting:** `Rendering/RayTracing/RTConfigFastTraceDynamic` (default 0).
  * `0x1ee97d0` copies it into the acceleration-structure manager's configuration byte `0x405af23`.
  * The two BLAS-flag builders (`0x5106f0`, `0x5107f0`) read that byte **on every BLAS build and every refit**.
  * Animated (updatable) geometry gets ALLOW_UPDATE + PREFER_FAST_BUILD natively, and ALLOW_UPDATE + PREFER_FAST_TRACE with the option. Both are valid D3D12 flag sets.
* **Not stored per BLAS:** the flags are recomputed each time. A BLAS built under one value and refitted (PERFORM_UPDATE) after the value changed is updated with flags that differ from its build. D3D12 does not allow that; the update must use the build's flags.
* **The copy routine has two callers:** device start (`0x1eeaf40`) and a later RT path (`0x1ef1370` via `0x1ef3620`). So the configuration byte can change mid-session.
* **Rev3 wrote it live:** it treated this row like the RT memory rows (owned while Master is On), so a menu change wrote the engine variable mid-session.
  * Your log line at 13:29:27, "RT acceleration-structure manager started with other RT memory values", is URT's diagnostic seeing exactly that state: menu value Fast Trace, engine configuration still Fast Build.
  * The log ends there. The game crashed after that.
* **Persisted state:** nothing is corrupted. The only persisted item is the menu value `URTX_RTASFastTrace=1`, and URT validates it (0 or 1) like every row.

**Hypothesis** (likely, not proven without a crash dump): the mid-session crash is the refit flag mismatch above. The game ran the second copy path (`0x1ef3620`) after your change, then refitted animated BLASes built as Fast Build with Fast Trace flags, and the device was removed.

**Not determined:** why later launches crash.
* With the value saved, rev3 applied it at start before ray tracing initialised, so every BLAS would be built and refitted consistently.
* Possible causes:
  * an untested engine/driver path for Fast Trace on updatable BLASes, which CDPR ships off;
  * a cause unrelated to URT.
* Step 1 of the recovery tells these apart. Your log is consistent with the later launches not reaching URT at all: URT rewrites its log at every start, and your file still ends at 13:29:27.
* I won't claim a cause for the launch crashes without the data from step 1.

**Performance potential (unmeasured):** PREFER_FAST_TRACE builds a higher-quality BVH for characters and swaying trees, so ray traversal through them gets cheaper; refits and builds cost more. It is a genuine but probably modest lever. That is why CDPR's default is Fast Build for updatable geometry.

## 3. Repair in R4
* **Session-fixed:** the trace mode is written once at game start and never during a session.
  * A menu change, Native / Auto, Master Off or a preset never changes it live; every change takes effect at the next start.
  * The description now says so in all 18 languages.
* **Only before ray tracing initialises:**
  * URT applies it only while the AS configuration still holds its pre-initialisation value (128 at `0x405af14`). Every BLAS, from the first, then has the same flags.
  * If ray tracing is already initialised, URT skips it for that session and logs "RT Animated Geometry Trace Mode not applied this session…".
* **Startup guard** (narrow, reversible, logged): covers only the three restart settings still under test (Async GI Classification, AS Async Compaction, Trace Mode).
  * **Where:** `Documents\The Witcher 3\UltimateRefinedTracing.startupguard`, a separate file that is safe to delete. It never touches `dx12user.settings` or `UltimateRefinedTracing.settings`.
  * **Before:** each chosen value is recorded as *pending* before it takes effect.
  * **Proven:** after 10 minutes of ray-traced (RT or PT) rendering in that session, it is marked *proven* and never blocked again, so later unrelated crashes cannot block it.
  * **Failed:** if the next start still finds it *pending*, that session ended early with the value in effect. URT does not apply it again and logs "startup guard: … not applied …". This prevents a crash loop.
  * **Retry:** set Native / Auto for one start, then choose it again.
  * **Fail safe:** if the guard file cannot be written, those three settings stay native for the session.
  * **Unaffected:** the approved settings (Async AO, Async GI Shading, the four preset rows) and all V5.2.0 rows.
* **Startup log:** every applied startup override is logged by name, e.g. "startup override applied: URTX_RTASFastTrace=1".
* **No other change:**
  * the WitcherScript and menu are byte-identical to the rev3 compile (same receipt, no new WCC run);
  * the PT shader is unchanged;
  * the other V5.3.0 controls and presets are unchanged.

**Offline evidence:** 47 / 47 host tests pass.
* `test_v530_image` (53 checks on the real executable): early start applies, late start is skipped, mid-session changes are never written, Master Off leaves the session value, the guard blocks after an early session end and leaves the approved rows alone, retry, proven after 10 minutes, and the no-guard-file fail-safe.
* `test_startup_guard` (12 checks): the pure guard logic.

**This does not prove Fast Trace is crash-free.** Only your test can show that.

## 5. R4 launch crash (2026-10-28 13:57): findings from the owner's log, guard file, settings and Windows report
**Confirmed**
* **Trace Mode was not involved:**
  * `dx12user.settings` [URTExtended] has `URTX_RTASFastTrace=0`; the menu change took effect.
  * R4 applied no Trace Mode: there is no "startup override applied: URTX_RTASFastTrace" line, and the guard file has no Trace Mode record.
* **R4 applied exactly four startup overrides:**
  * `URTX_RTAsyncAO=1` and `URTX_RTAsyncGIShading=1`: approved, and stable before.
  * `URTX_RTAsyncGIClassify=1` and `URTX_RTASAsyncCompact=1`: new, and this was their first effective start. Both were recorded `pending` by the guard, as designed.
* **The crash:** about 15 s after start, just after the first menu exit (log: Frame Generation "Keep Resources in Menus" at 13:57:56). Windows: `witcher3.exe`, exception `0xc0000005`, offset `0x1cfa664`.
* **What the faulting instruction is:**
  * `0x1cfa664` is in `CRenderTaskBatchProcessor` (function-table slot 2, `0x1cfa650`).
  * It indexes the device's command-context table: `[(handle − 1) × 64 + device + 0x268b858]`, the same table the async begin-pass helper `0x14050bd10` fills.
  * With handle 0 the index underflows, so a GPU command context that does not exist was used.
  * The game's own code ran with an engine flag that URT set at start; URT code was not on the stack. Nothing points to the R4 guard or to the Trace Mode logic.
* **Classification resources exist:** the async classification constant buffer is created unconditionally with the GI grid (`0x1c63998`, flags `0x503`), next to the synchronous one (`0x1c63966`).

**Inference (not proven):** the faulting row is most likely `UseAsyncCompact`.
* Compaction runs when new BLASes are built, i.e. while a scene loads, which matches the time of the crash after leaving the menu.
* Async classification runs every RT frame and had already run for about 13 s of RT frames (from 13:57:43) without a crash.

**Earlier report revised:** the post-incident rev3 launch crashes are also explained by these two rows; they were pending from the same settings. That the original mid-session crash came from Fast Trace is therefore no longer established. The R4 Trace Mode repair stays: it is correct regardless.

**R4 behaved as designed:** the next start finds both records `pending`, blocks both and logs it, so the game starts. No code change is needed for the guard to recover this case.

**Isolating the two rows:**
1. Start once (both blocked).
2. Set both to Native / Auto for one start, which clears the records.
3. Enable only Async Compaction, restart and load a save.
4. Then do the same with only Async GI Classification.
