## 3. Startup safeguard: what each time means

| Question | Answer |
|---|---|
| When does an optimisation start working? | From the **first** Path Tracing frame after a start. It is decided at ASI load, before the renderer exists; there is no waiting period. |
| When is a PT coverage option provisionally safe? | **R12 FIX4:** after **300 Path Tracing frames rendered with URT's variant**, about 5 s at 60 FPS. |
| When is an RT restart row (Trace Mode, Async GI Classification) stable? | After **1 minute** of RT/PT rendering, unchanged. |
| Clean exit | `DLL_PROCESS_DETACH` during normal process termination marks this session's options as clean, however short the session was. The next start applies them at once. |
| Interrupted session, before qualifying | Suspected start-up failure. The next start runs native **once** (logged with the reason), the one after retries automatically, and a second interruption turns the option off until Native / Auto is chosen for one start. |
| Interrupted session, after qualifying | Not treated as a shader failure: the option stays on. |

**Why frames and not 5 seconds of clock time:**
* The count only increases for frames whose CameraCB word carried the variant's level.
* A hung GPU stops frame submission (D3D12 keeps only a few frames in flight; a GPU hang leads to TDR device removal after about 2 s), so a hang cannot qualify.
* The PT variant's failure modes all show up in its first frames: state-object creation, validation, first dispatches.
* Clock time alone no longer qualifies a coverage option; for example, Master Off for a whole session leaves it pending.

**Why the RT rows keep 1 minute:**
* The two crashes on record for that kind of row (R4) happened when scenes loaded: Async Compaction about 15 s in, Fast Trace mid-session after a change.
* A 5-second window would qualify such a row before its failure could appear. That would allow a crash loop.
* The longer window never delays activation or blocks clean restarts; it only matters after an unclean end.

**The "10 minutes" log line** was stale wording. The logic was 1 minute since R12 FIX2; the line is corrected.

**Tests (OFFLINE, real image of both executables):**

*Rapid experimentation, 360 cycles:* change 1–4 settings (coverage rows, restart rows, others), start, play 0–10 s of PT (or quit at the menu), exit cleanly, start again immediately.
* Over the 240 cycles that all end cleanly:
  * every chosen option was applied at every start;
  * no suspected or failed record was ever created.
* Over the 120 cycles with random interruptions:
  * a held-back option always had a recorded, logged reason.

*Deterministic interruption cases:*
* interrupted before qualifying → native once, then retried;
* interrupted after 300 frames → still applied;
* two start-up failures → off, stays off, and one Native / Auto start re-enables it;
* 299 frames do not qualify, 300 frames do;
* 11 minutes without variant frames do not qualify.

## 5. Research (STATIC). Nothing below is implemented.

**GPU, outdoors** (Geometry Bounces 1, Diffuse 50 %, Sun Shadow 50 %). Per pixel, PT work now consists of:
* the bounce ray for specular samples and kept diffuse samples;
* its closest-hit shading;
* half of the sun / local shadow rays.

| Candidate | Finding |
|---|---|
| First-bounce **specular** coverage | Same mechanism as module 2. Specular is a small share of samples on foliage and terrain, so the expected saving is about a quarter of module 2's at best. Ray Reconstruction uses the specular hit distance, so dropped samples risk visible reflection flicker. It would also have to edit the same blocks as the measured module 2. Not implemented. |
| Foliage any-hit on shadow / bounce rays (force opaque) | R8 measured no gain, and the result is biased (solid leaves). Not repeated. |
| Contribution-adaptive shadow sampling | Needs a per-light contribution estimate before each trace. The sun site's estimate is spread over several values, and the gain over a flat 50 % is unproven. Research only. |
| Closest-hit / material cost (texture LOD in hit groups) | Lives in separate hit-group libraries and needs a second shader-replacement path. Still the largest untouched cost; a candidate for a later round. |
| Payload / memory traffic | The PT payload is a single `GbufferPayload` (`<4 x i32>` + i32). There is nothing meaningful to shrink. |

**CPU (STATIC, both executables):**
* **The game already sizes its own job system from the CPU's topology.**
  * The executable queries the topology itself (`GetLogicalProcessorInformationEx`, `GetSystemCpuSetInformation`) and assigns its threads with `SetThreadSelectedCpuSets`, `SetThreadIdealProcessor` and `SetThreadAffinityMask`.
  * CPU sets report each core's efficiency class, i.e. P-core vs E-core.
  * The job system (`CTaskScheduler`, `CTaskThread`) is built on that.
* The only thread-count setting it exposes is `ResourceLoading/Decompression/NumThreads`. That governs streaming decompression, not frame time.
* With Path Tracing at about 65 FPS on an RTX 4080 with DLSS Quality, the frame is almost certainly GPU-limited. More CPU parallelism would not raise FPS there.
* **URT's own CPU time per frame:** one serializer wrapper (a few atomics and memcpy calls) on the render thread, plus the 50 ms worker poll.
* **Not implemented:** no affinity, priority or thread-count change.
* **Simple check for the owner, no software needed:** at the benchmark spot, set DLSS to Performance. If FPS rises clearly, the scene is GPU-limited and a CPU change cannot help it.
