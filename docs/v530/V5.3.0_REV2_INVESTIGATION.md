# V5.3.0 PRIVATE rev2: investigation and implementation record

**Method.** All analysis is static and read-only: the Patch 5.01 `witcher3.exe` (`2df76539…`), the URT research tools in `tools/research/` (CVar registry, verified RIP-relative cross-references, annotated disassembly, RTTI), and the three supplied archives treated as reference material. No competitor code was executed, copied or bundled, and no shader was touched. **No figure here is a measurement**: every performance effect is unverified until you test it on the RTX 4080.

## 1. Corrections to the four gameplay-approved controls
| Item | Cause / change |
|---|---|
| Raw identifiers shown as titles | The game resolves a row title as `option_` + displayName. Rev1 added only the bare key. Rev2 adds both keys for every V5.3.0 row. A new test (1b) checks every row title the way the game looks it up, in 18 languages. |

| Master tooltip | Adds "Some settings require a game restart to take effect. Check each setting's description for details." Immediate restoration is qualified as "at once for most settings". |
| Log accuracy (found while testing) | Before RT initialises, the AS configuration word at `0x405af14` holds its static value 128, not 0. "RT memory settings applied before ray tracing initialised" therefore never fired. The check now treats 128 (or 0) as not yet initialised. Applied values are unchanged. |

**Async rows and Extreme.** These rows are session-fixed. Selecting Extreme (Native) relinquishes them at the next game start: the boot step then writes nothing and the game's own value (Off) stays. Nothing ever flips them mid-session.

All three use the existing table architecture:
- name + real category + flags + registered default + pinned RVA;
- compare-and-swap writes;
- never saved to `dx12user.settings`;
- Master Off: boot rows apply nothing at the next start, and the startup row is released.

The real-executable test (`test_v530_image`, now 31 checks) proves each binding, the boot/startup timing, that nothing flips live, and the Master Off image state.

## 2b. PT: Moon Light (owner's request; visual, not a performance control)
* **Engine variable:** `Rendering/RT/PathTracer/PTMoonImpact` (default 1.0). It is read live every frame by the PT constants writer: `0x1ef2a0e`–`0x1ef2a2e` computes Moon + (Sun − Moon) × day factor (clamped 0..1) into the PT constant at +0x21c.
* **Effect:** only the moon's direct light at night changes. It is independent of PT: Sun Impact, which is the day end of the same blend.
* **No shader change:** the protected PT library and Orange Hair Fix keep working.
* **Row:** placed directly beneath PT: Indirect-Light Compensation, the same OPTIONS row type as the other PT option rows.
  * Values: Native / Auto (1.00), 0.25, 0.50, 0.75, 1.50, 2.00, 3.00.
  * Applies immediately, PT only.
  * Master Off and Native restore the game value byte for byte.
  * It is in no Quick Preset.
* **Kit:** `v530priv-rev3` supersedes the uncompiled rev2.

## 3. Competitor archives
**A. LessStutter FPSBoost ShaderCache 1.0.8**
* **Mechanism:** a `d3d12.dll` proxy (vtable or function hooks) that records graphics, compute, root-signature and DXR state objects into `pipeline_cache.bin` (150 MB) and recreates them during loading. The optional installer contacts a community server; that code was inspected only, not run.
* **What the game already does:**
  * `PostProcess/LoadpsoCache` = 1 (default) loads and saves the game's own PSO cache, `psodx12.cache` (`0x2375cc0`/`0x2375d80`, 392-byte records, batches of 16,384).
  * `SkipDrawWithoutPSO` = 1 skips a draw instead of stalling while its PSO compiles.
  * A `Dx12PsoCacheManager` and `GamePipelineLibraryDx12.cache` exist.
* **Where its extra value is likely to come from:** DXR state objects. Its own notes say `CreateStateObject` "never persists to the driver cache".
* **Decision:** not implemented.
  * A comparable result needs D3D12 device hooks. URT deliberately has none, and Streamline/Frame Generation and RTXMFG hook the same device.
  * It would mostly duplicate the native PSO cache.
  * It cannot be validated offline.
  * It is a stutter (warm-up) effect, not an FPS effect.
* **Coexistence:** URT does not hook D3D12, so the two should coexist. This is untested.

## 4. Other candidates from the executable
* **`InlineRTAO`:** a real inline variant, registered and gated on a Shader Model 6.6 capability check (`0x1ecf8e6`). It selects between two PSO slots in a device-wide table, and the dispatch consumer could not be traced statically. A mismatch would be a device-removed crash on the first RTAO frame. **Deferred:** it needs a run-time check before exposure.
* **Already optimal:** `UseHighPriorityAsyncRT`, `UseAsyncTLASUpdates`, `UseAsyncDataUpdates`, `EarlyAsyncTLASUpdates`, `EarlyAsyncGIPrepareToShade` are all on by default.
* **Rejected:**
  * `RTDataDisableInternalUAVSyncs`: removes UAV barriers, a correctness risk.
  * `RTConfigForbidRefit` and `RTConfigRebuildEveryFrame`: more work.
  * `Budget/cvMaxAllowed*`: budget-warning thresholds, not limits.
* **PT:** SHaRC entries are allocated at init, a VRAM-only change with collision risk. Accumulation and stale frames are quality, not cost.
