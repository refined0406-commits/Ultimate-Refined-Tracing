## 1. Separator root cause

### The menu renderer [static]

Source: the shipped, unmodified `panel_ingamemenu.redswf`, read with URT's own AVM2 reader.

**Each visible list row is a recycled `W3SubMenuListItemRenderer`.**
- `createSubElementByType` runs every time a renderer is given a new row, which happens on every scroll step.
- It sends both `SEPARATOR` and `SUBTLE_SEPARATOR` rows to the same child object, `mcSeparator` (a `W3OptionsSeparator`).
- That object is created **once per renderer** (`if (mcSeparator == null) ...`) and then reused for every later row.

**`initSeparator` (named heading)**
- Sets `label.text = data.label` and then sets `width`.

**`initSubtleSeparator` (unnamed spacer)**
- Sets `label.text = ""`, `x = -150 + 300`, `width = width - 600` and a reduced `alpha`.

**`W3OptionsSeparator.width` setter**
- If `label.textWidth == 0`: `rightLine.visible = false` and `leftLine.width = full gap`. This draws a single line.
- Otherwise it sizes and positions both lines.
- It **never sets `rightLine.visible = true`**, and neither init function does either.

**Consequence**
- Any renderer that has once displayed a subtle spacer keeps its right-hand line hidden for every named heading it shows afterwards.
- RC3/RC4 had two subtle spacers in the Ray Tracing section. Scrolling past them handed "poisoned" renderers on to Texture / Streaming and Frame Generation.
- Scrolling back handed them to CPU, Path Tracing and Ray Tracing.
- This matches your report exactly: correct on opening, then broken after scrolling, and the damage spreads to every heading.

### Why RC4's one-byte patch changed nothing [static]

The resource holds two copies of the movie:
- a zlib-compressed GFx movie (`CFX`, bytes 1,890–323,004);
- a second, uncompressed SWF (`FWS`, bytes 323,008–4,851,231).

RC4's script searched the raw file for the bytecode. The compressed copy cannot match a raw byte search, so the script found and changed byte 4,575,497, which is inside the **uncompressed second copy**.

The compressed movie still contains the original `pushfalse`. Your in-game result is consistent with the game playing the compressed movie.

Even applied to the right copy, the patch would only have made subtle spacers draw a stale-width right line. It did not address the reuse.

### Why Immersive World's headings work [static]

- Its menu XML uses only `displayType="SEPARATOR"`. It has **no `SUBTLE_SEPARATOR` rows** on any page and ships no SWF.
- `tags="nonLocalizedName"` only makes the game show the literal name instead of a string key. It does not affect line drawing.
- URT keeps localised names (18 languages), which is equally supported: `initSeparator` just copies the resolved label.

## 2. The fix (smallest, native, no hooks)

### Menu XML

Remove the two unnamed `SUBTLE_SEPARATOR` rows (`URT52SEP_SMALL_RT` and `URT52SEP_SMALL_RTG`).
- Every other byte of the menu is identical to RC4.
- The diff is exactly the two deleted lines, checked by `tools/v52_selected/menu_delta.py`.

### Menu asset

`panel_ingamemenu.redswf` goes back to the unmodified file shipped since V4.3.1 / V5.1.0 / RC3 (sha `9a9f9c5a…`).
- The RC4 change is withdrawn.
- No Flash code is modified.

### What is kept

- The five named white headings (CPU, Path Tracing, Ray Tracing, Texture / Streaming, Frame Generation).
- Their 18-language strings, including the existing padding.
- All 45 controls, their order, options and Quick Preset entries.

### Visible difference

- The Ray Tracing section loses its two faint unnamed divider lines (under "Ray-Traced Optimizations" and before RTGI).
- There is no other visible change.

### Known limit [static, not verified]

Whether the game reuses renderers across different option pages is not established. If a *vanilla or other mod's* page that contains subtle separators is opened first, the same mechanism could, in principle, affect URT's headings in that menu session.

Checklist step 4 tests this. If it happens, the only remedy is a real SWF change in the compressed movie: an added `rightLine.visible = true` in the width setter. That change is not made here.

## 6. Graphics-settings integrity audit (read-only)

### Unchanged by RC5
RC5 changes no settings code, script, ownership logic or save call. Everything below applies equally to RC3/RC4.

### What protects the player's settings [static/offline]

- **The ASI has no writer for game settings.**
  - It imports no INI writer.
  - It opens `dx12user.settings` with `GENERIC_READ` only.
  - It writes only its own log.
- **MaxTextureSize (native Texture Quality) is never named by the ASI.**
  - The same holds for TextureMemoryBudget, TextureMipBias and TextureInFlightBudget.
  - The removal of Texture Memory Budget and Mip Bias is intact (`test_native_graphics_safety_rc3`).
- **Script saves**
  - The script calls `SaveUserSettings` in exactly 3 places, all after a URT or renderer row edit; this is unchanged.
  - There is no save at startup.
- **New rows are written by compare-and-swap ownership** (`urt_gfx_core`):
  - Native/Auto = no write.
  - Master Off, invalid settings or renderer change restores the value captured when URT took ownership, only if the live value is still URT's.
  - A foreign write makes URT release and, after repeated fights, yield.

### Remaining risk found by this audit [static; not observed in game]

**The mechanism**
- The game's settings save (function at `0x1426e7070`, 24 direct call sites) walks every registered engine variable.
- For each variable with the "save" flag (byte +0x19, bit 0), it writes the **current live value** into the user settings document and then writes the file.

**Which URT rows are affected**
- Five RC3–RC5 rows write such save-flagged variables:

  | Row | Variable |
  |---|---|
  | RT: AO Screen-Space Sampling | `EnableAOSSSampling` |
  | RT: HBIL | `UseHBIL` |
  | RT: AO Pre-Trace | `EnableAOPretrace` |
  | RT: Screen-Space Reflection Assist | `RtRadianceScreenSpaceTrace` |
  | Textures Streamed at Once | `TextureInFlightCountBudget` |

- The flag on each was confirmed in the static objects.
- The same applies to three V5.1.0 rows already accepted in earlier releases:
  - `AOPretraceQualityLevel` (RTGI AO quality);
  - `PTLateSpecularScreenSpaceTrace`;
  - `PTLateSpecularCheckerboard`.

**Consequence**
- While such a row is not Native/Auto, any game save (including the one after each URT menu edit) can write URT's value into `dx12user.settings`.
- If the game exits in that state, the next session starts with that value as the game's own. Native/Auto and Master Off then return to it, and uninstalling URT would not remove it.
- None of these is the Texture Quality variable. Whether the native Texture Quality option *includes* `TextureInFlightCountBudget` cannot be checked offline, because the game's graphics XML is not available here.

**Status**
- This is **not changed in RC5**, as instructed: no redesign of proven safeguards.
- Candidate remedy for a later RC: clear that variable's save bit only while URT owns it, and restore it on release.
  - The bit has exactly two readers in 5.01: this save loop and the document-to-variable load.
  - The remedy needs its own build and in-game test.
- Meanwhile, keep these rows on Native/Auto unless you are deliberately testing them.

## 7. Compatibility assessment

- **Orange Hair Fix RT+PT [static/offline]:** the ASI and PT shader identity are byte-identical to RC3/RC4, and no shader is added. Gameplay hair rendering is not re-tested by RC5.
- **Immersive World [static/offline]:**
  - URT ships none of its files (`verify_release`).
  - The `compat_evidence_iwo` test passes against IWO's installed files.
  - IWO ships no menu SWF, so URT's SWF does not replace anything of IWO's.
- **Menu asset and other mods:** RC5 ships exactly the `panel_ingamemenu.redswf` that V4.3.1 and V5.1.0 shipped. Interaction with other mods is unchanged from those public releases.
  - Pre-existing and unchanged: any other mod that also ships this file overrides it, or is overridden by it, according to load order.
- **Loader:** UAL 9.7.4 `winmm.dll` is unchanged. ASI-ONLY still coexists with an existing loader such as Witcher Native Bridge's `dinput8.dll`.
- Full gameplay compatibility cannot be claimed from static tests.
