# V5.0.0: security and packaging audit after the Nexus quarantine (2026-10-21)

* **Scope:** the protected V5.0.0 hotfix release (tag `v5.0.0-hotfix1`, commit db3ae3d, checkpoint `URT_V5.0.0_hotfix1`), V4.3.1, and the official Ultimate ASI Loader (UAL) 9.7.4.
* **Method:** read-only. No binary was changed, rebuilt for release or uploaded to any scanning service.

## 1. Conclusion
* **No packaging error was found.** No vulnerability was found that could explain the quarantine or that justifies a rebuild.
* **No malware indicator was found** in either archive. That covers network code, process injection, persistence, payload download, obfuscation/packing and hidden or nested executables.
* **Most likely trigger: `UltimateRefinedTracing.asi`.** It is the only executable present in **both** quarantined archives. It is new in V5 (no reputation yet) and is a small, unsigned, CRT-free x64 DLL that patches code in its host process. That profile matches what generic heuristic and ML detections such as `Trojan.Lazy` / `Gen:Variant.Lazy` react to.
* **What is not proven:** which file each vendor flagged. That needs the per-file "Bundled files" view of the existing VirusTotal reports (§4).
* **`winmm.dll` cannot explain the ASI-ONLY quarantine**, because ASI-ONLY does not contain it. Whether it adds detections to MAIN is unknown without the per-file VT data.
* **Recommendation:** keep the archives unchanged and request Nexus moderator clearance with the evidence below.

**`UltimateRefinedTracing.asi` = source.**
* A fresh two-pass build of commit db3ae3d reproduces the ASI (`8f64af34d3ce6f2c3361d89ad7c2bf058fff857e3e4452bdd050f001c40fd83a`) **and both archives byte for byte**.

**`winmm.dll` = genuine UAL 9.7.4, unmodified.**
* It is byte-identical to `dinput8.dll` inside ThirteenAG's official GitHub release asset `Ultimate-ASI-Loader-NoPDB_x64.zip` (v9.7.4). GitHub publishes that zip's digest as `e5860e7d9a1805267535b65749575b5e406cc6ea3325c7392189c578815045d1`, and the downloaded zip matched it.
* The loader is distributed renamed to `winmm.dll`, the documented UAL usage.
* It is also identical to `bin/x64_dx12/winmm.dll` in the Nexus UAL package you attached (zip `7fab3b3b…`).
* The release asset with PDB (`Ultimate-ASI-Loader_x64.zip`) contains a different, 3.6 MB build. URT ships the NoPDB build.

## 5. Native behaviour audit of `UltimateRefinedTracing.asi`
**Imports:** KERNEL32 and ADVAPI32 only.
* Versus V4.3.1 it adds only `CreateMutexW` (single-instance guard), `GetCurrentProcessId`, `GetFileSizeEx` and `ReplaceFileW` (atomic settings save).
* There is no networking DLL (`ws2_32`, `wininet`, `winhttp`, `urlmon`).
* There is no `OpenProcess`, `WriteProcessMemory`, `CreateRemoteThread`, `CreateProcess`, `ShellExecute`, `SetWindowsHookEx` or registry-write API.

**Dynamic loading:** only these, all documented:
* `dxcompiler.dll` → `DxcCreateInstance`, for shader handling;
* `shell32.dll` → `SHGetFolderPathW`, to find Documents;
* a check whether the loaded `winmm.dll` / `dinput8.dll` exports `IsUltimateASILoader` / `CR01ProxyIdentityTestOnly`, for the compatibility log.

**Strings:** no URL, domain, IP address, command line or shell reference. The only flagged pattern is the mutex name `Local\UltimateRefinedTracing.Runtime.`.

**Memory and code patching:** in-process only, against `witcher3.exe` Patch 5.01.
* Every patch site is first compared against the expected original bytes; URT refuses anything already changed.
* Protection is raised with `VirtualProtect`, the bytes are written, `FlushInstructionCache` is called, and the original protection is restored.
* Relay pages are allocated read-write and then switched to read-execute.
* A bone-read pointer slot is swapped with an atomic compare-exchange.
* All of this is the standard technique of game mods and is how URT's documented optimizations work.

**PE layout:**
* Sections `.text` RX, `.rdata` R, `.data` RW, `.pdata` R, `.reloc`. No RWX section and no packing.
* No resources, no version info, no overlay, no TLS callbacks and no Authenticode signature.
* `TimeDateStamp` is a reproducible-build hash, so it reads as a future date (2041); V4.3.1 shows 2080 for the same reason.
* Same toolchain and layout as V4.3.1.

**File access:**
* reads `witcher3.exe` once to verify its SHA-256 (CryptoAPI);
* reads `dx12user.settings` (never written);
* reads and writes only its own `UltimateRefinedTracing.settings`/`.bak`/`.corrupt` and `.log`;
* `DeleteFileW`, `MoveFileExW` and `ReplaceFileW` are used only on those URT files.

**Threads:** one worker thread (`CreateThread`) that waits on a change notification for the settings file.

**Hardening note (low severity, pre-existing, not a fix trigger):**
* The 96-byte bounce trampoline lives in `.data`. While it is installed, its page is left as `PAGE_EXECUTE_READWRITE`.
* This is identical in V4.3.1 and not reachable from outside the process. It happens only at runtime, so it is invisible to static scanners and cannot explain the detections.
* Possible later hardening: allocate the trampoline as RW and switch it to RX, as the relays already are. It is not changed in V5.0.0 because that would alter the tested binary.

## 6. What was not changed, and why
* **No rebuild.** No genuine defect was found, and changing signatures, layout, compiler or functionality to evade AV is excluded.
* **Optional legitimate improvements for a future version:**
  * a VERSIONINFO resource (product, company, description);
  * Authenticode code signing.

  Both improve reputation-based scanning, but both change the binary and would need a gameplay retest. Do this only if Nexus asks.
* **Untouched:** the difficulty hotfix, the PT shader, all optimizations, presets, translations, settings safeguards, OHF/IWO compatibility and all checkpoints. Tests ran 28/28 at db3ae3d, and the reproducible rebuild today is identical.
